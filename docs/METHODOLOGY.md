# Methodology

How each step works, why it is done that way, and where it falls short. File names refer to `scout/`.

## What the model sees

Each turn, Claude gets the system prompt (the workflow and rules, in `agent.py`), the tool definitions (`schemas.py`) and the whole conversation so far, including every search result and tool result. It keeps nothing between calls, so the full history is sent every turn. That is why prompt caching matters for cost.

The critic gets much less: the memo draft and the evidence list, nothing else.

## 1. Research

Claude splits the theme into a few segments, searches, and records companies. Search is Anthropic's server-side `web_search` tool. A run has 15 searches; at most 10 can be used in one turn, so some are left for fixing validation problems later. The prompt asks for independent sources (press, funding databases, regulators) rather than company websites.

**Limits.** What gets searched and which companies are picked is up to the model, so two runs on the same theme can find different companies. This step is not reproducible.

## 2. Link check

Every URL returned by a search is stored after normalising it (no scheme, no `www`, lower case, no trailing slash or fragment). Any URL Claude cites has to match one of them.

The point is to catch made-up links, a common failure of language models. The check is free and gives the same answer every time.

**Limits.** It shows a link was in the search results, not that the page supports the claim. Step 7 covers that.

## 3. Validation

`checks.py` applies these rules to every company:

| Check | Rule |
|---|---|
| Independent sources | at least 2 different domains, not only the company's own site |
| Links | every source appeared in this run's search results |
| Funding | has a source URL that is also in the source list; amount above 0 and at most 50bn; not below 10,000 (which usually means "33" was written for 33 million) |
| Founding year | between 1990 and the current year |
| Evidence | every claim has a URL, and that URL is in the source list |
| Completeness | rated on every criterion; description of at least 8 words |
| Duplicates | same name or same website is rejected when added |

Validation passes when every company is clean and there are at least five (three once searches run out). Otherwise Claude has to research more or drop companies, giving a reason.

These are ordinary data-quality controls (completeness, consistency, plausibility, traceability to a source), the same kind used in reporting pipelines.

**Limits.** The rules check structure, not truth. A company with two weak sources passes.

## 4. Scoring

Claude rates each company 1 to 5 on five criteria, with a written reason for each (whole numbers only, at least 15 characters of rationale):

| Criterion | Weight | A 5 means |
|---|---|---|
| Traction | 25% | clear evidence of customers, volume or revenue growth |
| Funding | 20% | recent sizeable round from credible investors, or profitable at scale |
| Differentiation | 20% | product or model that is hard to copy |
| Theme fit | 20% | squarely inside the theme and geography |
| Regulatory | 15% | licensed or partnered with a licensed institution |

The total is computed in code: `score = sum(weight × rating) / sum(weights) × 20`, which gives a scale of 20 to 100. The same ratings always give the same ranking, and the weights are visible and easy to change.

**Limits.** The ratings are the model's judgement, not measurements, and can differ between runs. The weights are my assumptions, not estimated from data. A difference of a few points between two companies means little; read the result as a ranking.

## 5. Ranking robustness

`robustness.py` re-ranks the shortlist in 1,000 scenarios. In each, every weight is multiplied by a random factor drawn uniformly from 0.5 to 1.5, then the weights are rescaled to sum to one. For each company it reports how often it ends up in the top 3, and its best and worst rank. The random seed is fixed, so the output is reproducible.

This answers the obvious question about any weighted score: would the conclusion change with different weights?

**Limits.** Only the weights vary. The ratings themselves are held fixed, although they are probably the larger source of uncertainty. The ±50% range is an assumption. Ties keep the original order.

## 6. Human review

The proposed shortlist is shown with scores and funding. The reviewer approves it, removes companies, or rejects it with feedback that goes back to Claude. The memo tool refuses to run until there is an approval. With `--auto-approve` the shortlist is accepted without a person, and the memo says so.

In the MCP server the question goes to the user through MCP elicitation. A client that can't ask the user gets an error, so the model can't approve on its own.

## 7. Memo and critic

The structured parts of the memo (ranked table, ratings and rationales, source links, robustness table, run stats) are generated by code from the recorded data. Claude writes only the prose: summary, trends, segments and recommendations.

The critic (`critic.py`) is a separate call to the same model. It sees the memo and the evidence list and returns every factual statement the evidence does not support, ignoring opinions, the 1 to 5 ratings and rounding. Score rationales are checked too, since they are printed in the memo. If it flags anything, the claims go back to Claude to source or delete; flags in a rationale are fixed with `score_candidate`. Ratings of approved companies are locked, so only the text can change. On the second round, anything still flagged is published in the memo under "open items".

A fresh call is used because a model asked to review its own answer in the same conversation tends to defend it.

**Limits.** This is one model checking another. It can miss things or flag too much. It compares the memo with the recorded evidence, not with reality, so wrong evidence passes.

## 8. Source check

`verify.py` runs after the memo, without a model:

1. Collect every claim: company evidence, funding amounts and market facts.
2. Download every reachable cited page once (15-second timeout) and strip it to text.
3. Take the claim's key figures. Years are ignored unless they are the only number, and single digits are ignored when larger numbers are present.
4. Look for each figure on the page, allowing for unit differences ("15.5M" matches "15,500,000", "1.70bn" matches "1.7 billion").
5. Mark the claim verified (all figures found), partial, not found, unreachable (page could not be downloaded) or no figures (nothing numeric to check, reported separately).

**Measured accuracy.** I read all 24 checkable claims from the example run against their pages (`handcheck.py`). Of the 23 marked verified, 19 were fully supported, 2 partly and 2 not. Three of the four failures were one funding round recorded as total funding; the fourth matched a "Tracxn Score: 49/100" instead of a company count. One claim marked not found was correct; that page loads its content with JavaScript. A sample of 24 from one run is small, so treat 83% as a rough figure.

**Limits.** A match shows the number is on the page, not that it means the same thing there. Pages that need JavaScript or a login can't be checked. Currencies aren't compared. European decimal commas ("1,7") can be misread. Pages change over time.

## 9. Cost control

Token counts come from each API response. The estimate uses list prices: uncached input at full price, cached input at 5%, cache writes at 125%, output at the output price, and $10 per 1,000 searches. The conversation is cached, so earlier turns are re-read cheaply.

The run stops when the estimate reaches the budget (default $1), after 40 turns, or after two replies in a row without a tool call. A checkpoint is written before each model call so a stopped run can be resumed.

**Limits.** The cost is an estimate. The real bill is in the Anthropic Console.

## 10. What is reproducible

| Same input, same output | Can differ between runs |
|---|---|
| validation, scoring maths, ranking, robustness test, Excel formulas, source check (if pages haven't changed) | which companies are found, the ratings, the memo text, the critic's verdicts |

`audit.jsonl` records every search, tool call, error, critic verdict and API call with a timestamp, so it is possible to trace how a conclusion was reached.

## 11. Evaluation

`evaluate.py` runs several themes without a reviewer and compares: share of companies clean on first validation, links not found in search results, critic flags, claims verified, cost and time. It is for checking whether a change to the prompt or the rules improved anything.
